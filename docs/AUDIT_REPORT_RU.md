# Отчет об аудите кода DayZ Server Manager

## 1. Введение
Данный документ содержит результаты технического аудита проекта `dayz-server-manager`. Аудит проводился по следующим критериям: актуальность стека технологий, оптимизация и производительность, завершенность функционала, безопасность и качество кода.

## 2. Технический стек и Архитектура
Проект представляет собой монолитное приложение на Node.js (TypeScript) с веб-интерфейсом на Angular.

*   **Runtime:** Node.js (рекомендуется v16+, но код совместим с более новыми версиями).
*   **Язык:** TypeScript 4.9.5.
*   **Backend Framework:** Express 4.18.2 + DI контейнер `tsyringe`.
*   **Frontend Framework:** Angular 16.1.7.
*   **База данных:** SQLite (`better-sqlite3`) — используется опосредованно (в зависимостях), основная конфигурация в JSON.
*   **Взаимодействие:** REST API, WebSocket (`ws`), Discord Bot (`discord.js`), RCON (UDP).

Архитектура построена на базе внедрения зависимостей (Dependency Injection), что является сильной стороной проекта, обеспечивая слабую связность компонентов и тестируемость.

## 3. Анализ актуальности (Dependencies)

Состояние зависимостей оценивается как **умеренно устаревшее**. Требуется обновление ряда ключевых библиотек для обеспечения безопасности и доступа к новым функциям.

### Критические обновления:
1.  **discord.js (`^13.17.1`)**: Версия 13 устарела и использует старый API Discord (v9). Актуальная версия — 14.x. Обновление критично, так как Discord постепенно отключает старые версии API. Требуется рефакторинг кода бота (изменения в Intents, Partials, API вызовах).
2.  **rxjs (`6.6.3`)**: Используется старая версия в UI (в Angular 16 обычно уже v7). Рекомендуется обновление до v7.
3.  **Angular (`16.1.7`)**: Не самая старая, но уже вышла v17 и v18 с новыми возможностями (Signals, Hydration). Обновление не критично, но желательно.
4.  **TypeScript (`^4.9.5`)**: Актуальная ветка 5.x. Обновление даст прирост производительности компиляции и новые фичи языка.

### Прочие зависимости:
*   `express`: v4 стабильна, v5 в бете. Можно оставаться на v4.
*   `node-pty`, `systeminformation` (через `processes.ts`): Выглядят актуальными.
*   `tail`: Библиотека давно не обновлялась, но свою функцию выполняет.

## 4. Оптимизация и Производительность

### Backend
1.  **Работа с файловой системой**:
    *   В коде много синхронных вызовов `fs.readFileSync`, `fs.writeFileSync`, особенно в методах инициализации (`SteamCMD`, `RCON`, `ConfigWatcher`). Это допустимо при старте, но в `LogReader` или при частых операциях может блокировать Event Loop.
    *   *Рекомендация:* Перевести I/O операции на асинхронные методы (`fs.promises`).
2.  **Мониторинг процессов (`Monitor` service)**:
    *   Используется поллинг процессов каждые 30 секунд.
    *   **Windows**: Используется `wmic`. Это тяжелая утилита, создание процесса `cmd` -> `wmic` потребляет ресурсы.
    *   **Linux**: Чтение директории `/proc`. Это эффективно, но перебор всех PID каждый раз может быть накладным на нагруженных системах.
    *   *Рекомендация:* Рассмотреть использование более специализированных нативных модулей для мониторинга процессов или увеличить интервал опроса, если сервер не требует мгновенной реакции.
3.  **LogReader**:
    *   Использует `tail` для отслеживания изменений. При очень быстром росте логов (спам ошибками) регулярные выражения и эмит событий на каждую строку могут создать нагрузку на CPU.
    *   *Рекомендация:* Добавить троттлинг (throttling) или буферизацию событий логов перед отправкой через WebSocket.

### Frontend
*   Используется `webpack-bundle-analyzer` для анализа бандла, что хорошо.
*   Приложение Angular 16 работает достаточно быстро, но стоит проверить использование `ChangeDetectionStrategy.OnPush` в компонентах для минимизации перерисовок, особенно в таблицах логов и карте.

## 5. Завершенность функционала

Проект выглядит функционально полным для заявленных целей (установка, запуск, мониторинг DayZ сервера).

### Недостающие элементы / TODOs:
1.  **Обработка ошибок**: В `index.ts` есть `// TODO report` и `// TODO save and report` в обработчиках `uncaughtException` и `unhandledRejection`. Механизм краш-репортов не реализован до конца.
2.  **HTTPS**: В `README.md` указано "Provide self generated/signed certificates for HTTPS" как TODO. Сейчас безопасность полагается на внешний Reverse Proxy.
3.  **Hooks**: Реализован только базовый набор хуков (`beforeStart`, `missionChanged`). Планировалось больше.
4.  **Ротация логов менеджера**: Нет встроенной очистки собственных логов менеджера (не игровых), они могут бесконечно расти.

## 6. Безопасность

1.  **Передача данных**: Веб-интерфейс и API работают по HTTP. Basic Auth передается в открытом виде.
    *   *Риск:* Перехват паролей администратора в незащищенных сетях.
    *   *Рекомендация:* Обязательное использование Reverse Proxy (Nginx/Traefik) с SSL, либо реализация HTTPS внутри приложения.
2.  **Хранение секретов**: Пароли RCON, Steam и пользователей хранятся в `server-manager.json` в открытом виде.
    *   *Риск:* При доступе к файловой системе злоумышленник получает все доступы.
    *   *Рекомендация:* Это стандартная практика для self-hosted решений, но можно добавить возможность шифрования конфига или чтения секретов из переменных окружения (ENV).
3.  **Запуск от root**: В документации есть предупреждение не запускать от root, но Dockerfile использует пользователя `dayz`, что правильно.
4.  **RCON**: Реализована защита от брутфорса (хотя бы через таймауты и задержки реконнекта), но нет явного бана IP при переборе паролей RCON менеджером.

## 7. Качество кода

*   **Стиль**: Код чистый, типизированный, используется ESLint.
*   **Архитектура**: Хорошее разделение ответственности. Сервисы (`SteamCMD`, `RCON`, `DiscordBot`) изолированы.
*   **Типизация**: В большинстве мест строгая, но встречаются `any`, особенно при работе с внешними библиотеками или динамическими структурами конфига.
*   **Конфигурация**: Используется `Reflect.metadata` для валидации конфига — интересное и гибкое решение.

## 8. Итоговое заключение

Проект `dayz-server-manager` представляет собой **качественное, архитектурно продуманное решение**. Оно выполняет свои функции, но технологический стек начинает устаревать (особенно в части Discord.js и Angular).

**Приоритетные задачи для развития:**
1.  Обновить `discord.js` до v14 (Critical).
2.  Реализовать механизм ротации собственных логов.
3.  Добавить поддержку HTTPS "из коробки" или Docker Compose пример с Nginx.
4.  Перевести синхронные операции с файлами на асинхронные.
